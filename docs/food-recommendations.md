# แนะนำอาหารตามประวัติและเป้าหมาย

อัปเดตล่าสุด: เพิ่มความชอบโดยตรงและการจับคู่ชุดมื้อแล้ว ดู [รายละเอียดข้อ 2–5](features-2-5.md) ซึ่งขยายจากระบบจัดอันดับเดิมด้านล่าง การเก็บความชอบในบัญชีต้องรัน migration ใหม่

เพิ่มตามคำขอผู้ใช้เมื่อ 9 ตุลาคม 2026 ในหน้า **เพิ่มอาหาร → ค้นหาอาหาร** เมื่อยังไม่กรอกคำค้นหรือเลือกอาหาร จะแสดงส่วนแนะนำก่อนรายการ catalog

## การใช้งาน

เลือกวันที่ หมวดอาหาร มื้อที่จะกิน และแนวทางการแนะนำ:

| แนวทาง | น้ำหนักความคุ้นเคย | น้ำหนักตามเป้าหมาย |
|---|---:|---:|
| เน้นเมนูคุ้นเคย | 85% | 15% |
| สมดุลความชอบและเป้าหมาย (ค่าเริ่มต้น) | 40% | 60% |
| เน้นตามเป้าหมาย | 15% | 85% |

แสดง 6 รายการพร้อมเหตุผลและปริมาณที่จะใช้ กดเพื่อเปิดฟอร์มบันทึกเดิม ปรับปริมาณและมื้อได้ก่อนบันทึก ตัวเลือกแนวทางเป็นสถานะของส่วนแนะนำ ไม่ได้บันทึกเป็นค่าตั้งค่าถาวรของบัญชี

## ข้อมูลและคะแนน

- ใช้ `food_logs` ของบัญชีที่แอปโหลดมาแล้ว ประวัติยังอยู่หลัง refresh ผ่าน Supabase และคำนวณคะแนนใหม่จากประวัตินั้น ไม่ต้องเพิ่มตารางหรือรัน migration
- Guest ใช้ประวัติใน memory เท่านั้น เมื่อ refresh ข้อมูลและนิสัยที่อนุมานจะหาย
- ใช้ประวัติย้อนหลัง 90 วันจากวันที่เลือก ไม่รวมวันที่หลังวันนั้น ความชอบเป็นการอนุมานจากสิ่งที่บันทึก ไม่ใช่การยืนยันว่าผู้ใช้ชอบหรือกดรายการโปรด
- คะแนนความคุ้นเคย: 50% จำนวนวันที่กิน (เต็มที่ 7 วัน), 30% จำนวนวันที่กินในมื้อเดียวกัน (เต็มที่ 4 วัน), 20% ความล่าสุดแบบ exponential decay ระยะ 30 วัน การเพิ่ม log ซ้ำในวันเดียวไม่เพิ่มจำนวนวัน
- คะแนนตามเป้าหมาย: 65% ความใกล้เคียงกรอบพลังงานมื้อ + 35% ความเหมาะสมกับโปรตีน/คาร์บ/ไขมันที่ยังเหลือจากเป้า โดยคิดตามปริมาณของรายการจริง เครื่องดื่มและของหวานลดคะแนนส่วนนี้ครึ่งหนึ่งในมื้อหลัก
- กรอบมื้อใช้สัดส่วนเป้าพลังงานวัน: เช้า 25%, กลางวัน 35%, เย็น 30%, ของว่าง 10% หักรายการที่บันทึกแล้วในมื้อนั้น และไม่เกินพลังงานที่เหลือทั้งวัน ตัวเลขนี้เป็น heuristic ของผลิตภัณฑ์ ไม่ใช่สูตรโภชนาการที่ผ่านการตรวจรับทางคลินิก
- เป้าพลังงานและสารอาหารมาจากโปรไฟล์เดิมของผู้ใช้ จึงปรับตามเป้าลดน้ำหนัก/รักษาน้ำหนัก/เพิ่มกล้ามเนื้อ โดยไม่แก้สูตรคำนวณโปรไฟล์
- ลดคะแนนรายการที่กินในวันที่เลือกแล้ว 0.08 เพื่อเปิดโอกาสให้รายการอื่นขึ้นมา ผูกคะแนนด้วย stable ID เพื่อให้ผลเรียงซ้ำได้
- แหล่งรายการคือ catalog และอาหารส่วนตัวปัจจุบัน ใช้ `catalog:id` และ `custom:uuid` แยกกัน ไม่เอา AI/edited snapshot ที่ไม่มี identity ของรายการมาเดาว่าเป็นอาหารเดียวกัน

## หน่วยและกรณีไม่มีข้อมูล

- โภชนาการใช้เฉพาะอาหารที่มี `servingSize` และหน่วยชัดเจน ถ้าเป็น portion ต้องมีชื่อหน่วยที่ไม่ใช่ “ไม่ระบุ”
- ใช้ค่ามัธยฐานแบบเลือกค่ากลางบนของปริมาณที่เคยกินในมื้อเดียวกันเมื่อหน่วยเทียบกันได้ ปรับตาม serving size ปัจจุบัน; ไม่แปลง g เป็น ml และไม่ย้าย portion ข้ามชื่อหน่วย/น้ำหนักที่เปลี่ยนไป
- ถ้าไม่มีปริมาณเดิมที่เทียบได้ ใช้หนึ่งปริมาณอ้างอิงตาม catalog พร้อมแสดงจำนวนจริง จึงอาจเป็น 100 g ไม่ใช่หนึ่งมื้อทั้งหมด
- อาหารหน่วยเก่าแสดงได้เมื่อมีประวัติในโหมดคุ้นเคย/สมดุล พร้อมข้อความว่าแนะนำจากประวัติเท่านั้น ไม่อยู่ในโหมดตามเป้าหมาย
- เมื่อใช้พลังงานถึงกรอบแล้ว โหมดตามเป้าหมายไม่มีคำแนะนำเพิ่ม แต่ผู้ใช้ยังค้นหาและเลือกอาหารเองได้ โหมดอื่นระบุว่าไม่ได้ประเมินความเหมาะสมกับมื้อนี้
- ถ้า catalog ยังไม่ระบุหน่วยและไม่มีประวัติ จะบอกว่ายังไม่มีรายการที่ประเมินได้ โดยยังแสดง catalog ตามปกติ
- ใช้เฉพาะข้อมูลที่บันทึก ระบบยังไม่มีข้อมูลแพ้อาหาร/โรคประจำตัว และไม่ได้วางแผนอาหารครบมื้อหรือใช้ Gemini สำหรับการจัดอันดับนี้

- `frontend/src/lib/recommendations.ts`: คำนวณคะแนนอย่างเดียว ไม่เก็บข้อมูลบัญชีไว้ข้ามการเรียก
- `frontend/src/components/FoodRecommendations.tsx`: ตัวเลือกและรายการแนะนำ
- `FoodLogger` ส่งมื้อ/วันที่/หมวดและรับปริมาณกลับเข้าแบบฟอร์มเดิม; `App` ส่งประวัติและโปรไฟล์ของบัญชีปัจจุบัน และเปลี่ยน component key ตามบัญชี
- Tests ครอบคลุมเปลี่ยนน้ำหนัก/มื้อ/วันที่/เป้าหมาย, recency, หน่วยไม่ชัด, เปลี่ยน reference size, custom ID, budget หมด, ข้อมูลผิดรูปแบบ, เปลี่ยนข้อมูลบัญชี และบันทึกปริมาณจากคำแนะนำ
